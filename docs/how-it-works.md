# 一根线接上以后，究竟发生了什么

手机能录音，Mac 能播放声音。先把这两件事拆开，USB LinkMic 的麦克风功能就没那么神秘了。

Android 拿到系统录音许可后，用 AudioRecord 采集 PCM。你可以把 PCM 理解成按顺序排好的声音采样，手机把这些采样送到 Mac，Mac 再按实际格式交给音频设备。电平来自收到的采样，不是一个装饰用的动画。

USB 在这里提供的是一条传输通道。ADB 建好映射后，两端通过 socket 通信，手机没有伪装成系统原生的 USB 声卡。Wi-Fi 换掉的是传输路径，采集与播放仍是同一件事。配对码负责限制谁能接入，这条局域网音频链路本身没有加密，所以只放在信任的网络里使用。

声音到了 Mac，还差最后一段路。

本机试听把声音送到扬声器或耳机，别的软件不会因此多出一个麦克风。要让会议软件听到手机声音，需要一个可以被它选作输入的设备。USB LinkMic 把声音送进 BlackHole，会议软件再从 BlackHole 读出来。[BlackHole 官方说明](https://github.com/ExistentialAudio/BlackHole)里讲的就是这种应用之间的音频传递。驱动由你单独安装，USB LinkMic 不会自动装它。

网络要另外看。

手机给 Mac 供网时，程序让手机进入 USB NCM 模式，再通过 Android 系统的共享能力，把手机这一侧的网络接到 USB 网卡上。Mac 得识别到正确的手机网卡，链路有效，也拿到地址，才算连接准备好了。Android 版本、厂商 ROM、USB 重枚举和 Mac 网络服务，都会影响这一段。

有了 USB 网卡，并不保证 Mac 的所有流量都走它。

如果 Wi-Fi 还在工作，系统仍可能优先选择 Wi-Fi。应用会显示当前出口，但不会为了让一个绿灯亮起来，去重排你所有的网络服务。你需要手机网络作为出口时，再去系统网络设置检查它的优先顺序。

反过来，Mac 给手机供网，需要把手机的网络请求送回 Mac。这一侧用 Android 的 VPN 接口接住数据，再经 USB 转发给 Mac 上的 relay。转发组件来自 Gnirehtet，当前范围是 IPv4 TCP 和 UDP。这里的 VPN 是本地转发入口，不代表你订阅了某个 VPN 服务，也不代表自动获得加密或匿名访问。

两条路径都不要求手机 root，也没有自己开发驱动。代价是要接受系统已有能力的边界，尤其是不同 ROM 的共享接口。

连接和互联网是否通畅，是两件不同的事。

早期版本会拿公网目标做健康探测，目标超时后又主动恢复 USB，结果把刚接上的连接拆掉了。后来按维护者的实际需求改掉了这条规则。现在「已连接」只报告链路就绪，公网网站访问失败不会单凭这一点触发拆线。真正的设备断开、转发程序退出、VPN 被系统收回，仍会显示状态变化。

停止也得算在功能里。

程序会记录这一次创建的转发、进程和 USB 改动，先确认手机任务取消，再恢复自己改过的部分。原本就存在的共享，只借用，不顺手关掉。恢复失败时保留记录和错误，不能把按钮变回「开始」就当作事情结束。

这就是整个项目的出发点，手机已经有的麦克风和网络，给它们接一条能看清、能停下来的路。
